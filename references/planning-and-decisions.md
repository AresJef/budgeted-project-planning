# 步骤、核心决策与完成门槛

制定或修订项目计划、处理核心未决问题、设置验收条件和进度权重时，读取本文件。先按入口确认总预算和授权，再在已分配的规划预算内核实资料。

### 项目输入

- 项目名称：[填写]
- 项目位置：[填写本地目录或项目入口]
- 项目背景与已有资料：[填写或引用交接说明]
- 本次最终目标：[填写最终交付物和实际能力]
- 明确包含与排除的范围：[分别填写]
- 已确定的决定：[填写；已有决定不得重新询问]
- 功能与兼容要求：[填写]
- 性能目标与必须保护的指标：[填写]
- 安全要求：[填写本次实际需要处理的风险]
- 代码与文档要求：[填写覆盖范围、语言、类型注解、注释和检查要求]
- 首次验收平台与运行环境：[填写]
- 完整项目总时间预算：[填写有效经过小时或分钟；未明确时必须先询问]
- 计时起点与已有用时：[原 T0、既定计时口径、累计用时及暂停记录]
- 截止时刻（如有）：[填写日期、时刻和时区；与总预算分别记录]
- 阶段硬上限（如有）：[仅填写用户明确指定的限制]
- 本次授权范围：[默认只完成规划；已有实施授权则沿用]
- 计划、台账与交付位置：[沿用项目既定位置或用户指定方式]

缺少信息时，先从项目资料和当前状态中核实。普通代码组织、工具选择和执行顺序可以合理判断并说明；影响目标、范围、行为、质量门槛、授权或重大成本的取舍，才需要用户决定。

## 把项目拆成明确步骤并逐步设置预算

以实际成果划分步骤，每一步都要能说明“做完后多了什么、如何证明”。步骤可包含连续的小操作；不能把大段不透明的工作笼统写成“开发”“完善”或“继续调查”。

规划与起点核查可以交付已核实的基线、明确缺口或可执行计划；实施步骤交付实际能力；验证步骤交付可判定的证据。每项必要要求都要落到具体步骤，不藏在“顺便处理”中。

先按成果和真实依赖确定顺序，再为每一步设置有依据的目标时间预算。近期步骤细化到可以直接执行；远期步骤也必须有成果、依赖和暂定预算，可附估算范围与不确定性，进入执行前细化，不留无预算的工作。

### 每步执行模板

以下字段可以写在同一张台账中，不必为每一步单独建文件。

- 步骤 ID 与名称：[唯一、稳定，例如 S03 完成安装通路]
- 实际交付：[对应哪个目标缺口，交付什么能力、文件或确定结论]
- 验收与证据：[通过条件、验证方法、证据位置；复用证据须注明有效性]
- 依赖：[前置步骤、环境、必要决定；没有则写无]
- 原定目标预算：[有效经过分钟；设置时的依据、主要不确定性]
- 执行记录：[实际执行区间、累计实际用时、与原定预算的差额]
- 剩余估算：[还需多少分钟、依据是什么、预计能否在总预算内完成]
- 当前目标与检查点：[初始沿用原预算；调整后记录新目标、有限追加用时及预期证据]
- 当前状态与下一动作：[未开始／进行中／待验收／通过／受阻／需修正；下一项具体操作]
- 验收权重：[仅完整模式填写固定分值；轻量模式省略]

差额按“累计实际用时减原定目标预算”记录，正数表示超支。调整目标另列，原定预算和实际差额始终保留，不能通过重命名、拆分步骤或重新估算把超时归零。

步骤预计超过约两小时，或包含多个可独立交付的成果时，应检查是否需要按真实成果拆分。拆分须保留原步骤映射、已经使用的时间、原预算及必要验收，不只更换标题。步骤通过且证据有效后停止扩展。

### 最小可执行循环

1. 开始前：核对本步交付、依赖、原定预算、下一动作，以及总预算能否容纳它和必要收尾。
2. 执行中：优先取得能缩小目标缺口的成果，记录关键证据和实际用时。
3. 完成时：核验通过条件，更新状态、实际差额与剩余预测，再进入下一步。
4. 超时时：在首个安全边界立即按 [预算与超时规则](budget-and-overrun.md) 自查，明确是否继续以及如何继续。

轻量任务可把以上字段压缩成简短清单，但不能省略明确步骤、每步预算、结果验证和超时自查。

## 核实真实起点、核心决策与完成门槛

### 核实项目起点

1. 检查工作目录、项目规则、工作树和已有修改，保留用户已有成果。
2. 阅读必要交接资料、相关源码和验证记录。已读且未变化的资料不重复全面调查。
3. 区分已有有效验收证据、已经实现但未验收、已经调查或规划，以及尚未开始的工作。
4. 存在冻结参考版本时默认沿用，不随上游更新自动替换。
5. 核实关键工具和运行环境是否可用。规划期间以只读检查为主，不把安装、实现或发布混入规划。
6. 探针、局部测试和一次构建，只证明其实际检查范围，不能冒称完整验收。

只读取直接适用的 skill，简要说明采用哪些做法。不机械叠加所有 skill，不因 skill 建议增加例行批准、重复记录或不必要的协作角色。

### 核心决策确认

将“核心决策确认”列为分步计划中的明确步骤，沿用本文件的步骤预算、验收与记录要求，交付必要问题、已确认结论及未决依赖。

在前期步骤预算内了解项目，只核查足以识别关键缺口和支持决定的资料，不为穷尽所有细节持续调查。进入依赖相关决定的实施步骤前，集中提出本轮已经能够识别、尚未明确且必须由用户决定的核心问题：

- 最终目标、包含或排除的范围，以及存在冲突的交付要求。
- 可观察行为、兼容性、错误语义或用户可见结果的改变与取舍。
- 会带来长期技术锁定、显著迁移负担、重大成本或难以撤销约束的技术方案取舍。
- 必要质量门槛、授权或安全边界中缺失、冲突或需要改变的要求。

每个问题简短说明：已核实的背景事实、可行选项、推荐及理由、各选项对行为和质量、时间或成本的实际影响，以及被阻塞的步骤 ID。相关问题尽量合并提出，避免逐项打断；不要把普通实现细节包装成核心决策。

自行判断普通代码组织、工具选择、执行顺序和既定范围内的技术选择。已有决定和授权直接沿用，不重复询问。没有需要用户决定的核心问题时，明确说明并按既定授权和预算继续，不人为制造批准环节。

收到决定后，将结论及适用范围原位写回当前计划，更新有关依赖、范围和验收条件，再推进依赖该决定的步骤。未回答不等于同意；不受影响、已获授权且仍有预算的工作继续，不让无关问题阻塞全部实施。

执行中出现新的核心问题时，及时按同一规则处理，不等到项目末尾才提出。必要等待按既定时间口径单列；等待期间仍推进独立工作时照常计入预算。

### 区分目标性质与批准差异

用一至三句话说明最终交付物，以及完成后用户能获得的实际能力。将重要要求分为三类，并对应到具体步骤：

| 类别 | 含义 | 完成判定 |
| --- | --- | --- |
| 必须交付 | 本次必须达到的功能、兼容、安全、安装、文档或性能要求 | 未通过不能宣布完成 |
| 必须保护 | 本次改动不得破坏的已有能力或指标，包含明确允许的退步范围 | 违反保护门槛时不能采用相关改动 |
| 可选优化 | 不构成完成门槛、预算允许时可以争取的进一步改善 | 未达到不阻止必要成果交付 |

优化目标若被明确约定为必须达到，就归入必须交付。不能在结束时新增“全部场景都必须获胜”等要求，也不能把未通过的必要验收改成可选项。

批准差异和已接受取舍单独登记，写明具体行为或指标、适用范围、批准依据和验收影响；它们不与可选优化混为一类，也不能由执行 Agent 自行推定。

保持原行为与修复缺陷或提高安全性发生冲突时，给出具体输入、两种结果和实际影响，纳入核心决策确认。不得修改冻结参考来掩盖差异。

明确包含和排除的功能、接口、平台、兼容行为与交付内容，并与已确认的核心决定一致。

### 固定可判定的验收标准

- 功能：结果、返回类型、错误语义和必要边界。
- 兼容：必须保留的行为、明确排除的部分和批准差异。
- 性能：比较对象、场景、计时边界、统计方法、目标和允许退步范围。
- 安全：本次实际可达的输入、计算、状态和资源风险。
- 代码与文档：覆盖范围、必要说明和检查方式。
- 安装与交付：构建、实际安装、加载、使用和复现方式。
- 平台：实际验收环境及未验证环境的限制。

避免“基本一致”“性能较好”“安全可靠”等无法判断的表述。未经实际运行的命令和操作标为“待实施验证”。正式性能比较前固定输入、指标、权重、环境、采样和通过规则，不事后调整来掩盖退步。

代码与文档要求必须具体说明：

- 覆盖本次改动，还是整个维护模块；是否包含已有代码。
- 哪些接口、参数、返回值、错误、所有权或资源生命周期需要说明。
- 必要的注释、docstring、类型注解、示例和文档语言。
- 格式、静态检查及文档构建的要求。
- 起点已有问题如何记录，以及本次不得引入哪些新问题。

文档随实现完成，纳入所属步骤验收。不要求逐行解释显而易见的代码，也不为数量机械增加注释。预算明显无法容纳必要验收时，尽早报告依据和缺口，不给未经验证的完工保证。

## 安排实施顺序并报告真实进度

### 实施顺序

1. 先打通最小可运行、可安装或可使用的交付通路。
2. 按真实依赖推进，每完成一步尽量取得可验证能力。
3. 高风险且影响后续整体实现的事项提前验证。
4. 复用必要的输入、环境、运行器和构建缓存，避免重复准备。
5. 性能是主要目标时，首个关键功能可运行后进行早期测量。
6. 不把所有验证拖到最后，也不在每个小改动后无差别执行全量检查。

阶段用于汇总相关成果和时间安排；执行仍落实到具体步骤。阶段和步骤数量由成果与依赖决定，不为显得详细而增加管理工作。

### 完整模式的验收进度

完整模式将全部必要成果的固定权重合计为100分，可选优化不用于稀释必要成果的分母。

- 总项目验收完成率＝当前有效通过分值÷100。
- 阶段验收完成率＝该阶段有效通过分值÷该阶段固定总分值。
- 未开始、进行中、待验收、受阻和需修正的步骤均不计通过分。
- 证据失效时撤回受影响分值，不无差别作废无关成果。
- 父级只汇总，不能与子步骤重复计分。
- 拆分步骤继承原权重，不通过拆项、删项或改变分母提高进度。

100分表示加权验收完成率，不代表工时、工作量或未来完成概率；必要门槛仍须逐项通过。代码量、测试数量和投入时间不能代替成果验收。

进度同时说明实际已实现、已验收的功能或类型数量，以及阻止下一步的具体缺口。没有新增通过分值时，也说明是否取得有效结果、缩小失败范围或消除了阻碍。

轻量模式直接报告步骤状态、实际成果和剩余缺口，不强行折算百分比。两种模式均从同一台账获取状态和时间信息。
